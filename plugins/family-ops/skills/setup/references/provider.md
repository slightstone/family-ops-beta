# Provider configuration and human authorization

Provider configuration must be supported and separately qualified before asking the customer to start its trial. Credentials belong only in their Site's native runtime secrets through an approved secure path. Never ask them to paste secrets in chat, model arguments, source, screenshots or schedule prompts. Signup terms/password entry and QR require the customer. Disclose provider-wide initial sync/storage before QR: downstream group selection does not limit all upstream synchronization. Trial and paid-provider charges are separate from AI/Sites allowances. A provider API read is not native cloud schedule acceptance.

**Verify the provider version before signup or secret access.** This adapter uses [Unipile V2](https://developer.unipile.com/v2.0/docs/welcome), with its dashboard at [dashboardv2.unipile.com](https://dashboardv2.unipile.com/) and new-account registration at [dashboardv2.unipile.com/register](https://dashboardv2.unipile.com/register). The older dashboard.unipile.com/signup route creates a V1 account. V1 and V2 dashboard accounts are separate; a successful V1 signup, DSN or Access Token does not configure this V2 adapter. Check the visible V2 dashboard and the customer's actual organization/application/environment before any customer-controlled protected key entry. If the customer has only V1, explain the mismatch and prepare the correct V2 form; do not reuse a V1 key, migrate accounts/subscriptions, pair WhatsApp, accept terms or submit a new account without the required owner action/approval. Confirm the actual V2 trial and eligibility separately; V1's trial status does not prove a V2 trial exists.

Use this reviewed release’s PRIVATE polling path. After the owner’s exact provider-account, credentials and wider initial-sync approval, have the customer configure their own Site runtime only through a qualified protected host entry path (never assistant-visible secret values): FAMILY_OPS_KIDS_LIVE=enabled, FAMILY_OPS_KIDS_HOSTED_SOURCE=unipile-v2, FAMILY_OPS_KIDS_HOSTED_TRANSPORT=poll, FAMILY_OPS_PUBLIC_ORIGIN=the actual own Site origin, UNIPILE_APPLICATION_ID=their actual provider application, UNIPILE_ENVIRONMENT=the actual test or production environment, UNIPILE_API_KEY=their own key, and FAMILY_OPS_SOURCE_IDENTITY_KEY=a fresh random32-byte secret. Use the provider’s actual account/application setup, never invent IDs. Do not configure a webhook endpoint, webhook secret, public callback workaround or bearer in a URL. Preserve all three installation metadata values. Actual secret handoff must be secure and separately accepted; do not collect credentials in chat. A trial with its own organization may have a separate paid minimum after the trial; do not imply $5.50flat for a single household.


After the exact approved configuration is deployed, use the current [source proposal workflow](source-setup.md). Add and Reconnect name different exact targets. A returned HTTPS auth.unipile.com link is transient: hand it to the parent for QR/sign-in, never store or log it. After an expired return use check-paired for the saved setupId; never guess a binding or start another QR to bypass an unknown result. No source bodies before exact chat/person tracking approval.

Cloud execution is a separate acceptance boundary. After an interactive real source/model/save/readback succeeds, inspect existing native schedules before proposing one exact recurring source workflow. Keep credentials and raw records out of prompts. Test an actual new message with all buyer computers off; compare source evidence, saved board and phone. A saved-board-only run is insufficient. Preserve visible coverage/auth gaps and source cursors; never substitute a local daemon, API model or another family account.


## Qualified protected Sites entry; keep secrets out of chat

For the supported ChatGPT web Sites settings surface, match the exact customer project and signed-in owner before entry. New variable names and secret toggles may autosave immediately; do not assume an uncommitted draft or an explicit Save button. Establish Treat as secret before entering any value. A saved secret's Replace secret action opens a password field. Enter commits the replacement; wait for Saving then Saved and verify protected metadata/configuration revision. Entry alone is not saved evidence. Reload before further UI edits if native tools changed configuration, so a stale form cannot overwrite new entries. Preserve all unrelated keys and original identity.

Provider one-time controls differ. A copy button is not necessarily a selectable text input, and a page clipboard may not bridge to an automation clipboard. Do not extract or return the value through tools, prompts, files or screenshots to work around that limitation. If a qualified protected native transfer is unavailable, have the customer click Copy and paste directly into the exact password field, press Enter and wait for Saved. Never ask for the key in chat. One-time creation is not safely repeatable after an uncertain result. Respect required action-time credential confirmation and any existing control denial.

Use the adult's current explicit authorization for routine setup within its stated scope; do not invent redundant conversational approvals for pure technical checks. Retain genuine parent review of exact source scope, provider terms/cost, QR, selected chats and Calendar operations. This guidance is based on an internal host test; another host's controls and independent buyer setup remain unverified.
